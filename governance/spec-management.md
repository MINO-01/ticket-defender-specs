# Ticket Defender 명세 관리 정책

## 범위와 증거

`00`~`15` 문서는 목표 설계의 원본이며, `ALL_통합_명세서.md`는 순서를 유지해 만든 검색용 파생본이다. 원본에 없는 의미를 통합본에 독립적으로 추가하지 않는다. Specs 문서의 승인 여부와 Backend·Data·Frontend의 구현 여부는 별개의 사실이다. 실제 구현 판단에는 저장소의 정확한 commit SHA, 코드 위치, 검증 결과와 범위를 기록한다. 과거 테스트 기록은 다른 HEAD의 합격을 보증하지 않는다.

## 상태

| 문서 승인 상태 | 의미 |
|---|---|
| DRAFT | 초안 또는 관리 문서의 검토 전 상태 |
| PROPOSED | 구체적 검토 제안, 승인 전 |
| APPROVED | 승인자·시각·근거 PR이 기록된 적용 기준 |
| DEPRECATED | 새 revision으로 대체되어 이력만 보존 |

| 코드 구현 상태 | 의미 |
|---|---|
| NOT_STARTED | 해당 계약의 구현 근거가 없음 |
| PARTIAL | 일부 코드가 있으나 계약 또는 경계 조건 미충족 |
| IMPLEMENTED | 적용 commit과 기능 범위가 확인됨 |
| VERIFIED | 적용 commit 및 해당 commit에 대한 실제 검증 SHA·범위·결과가 기록됨 |

`APPROVED`는 `IMPLEMENTED`나 `VERIFIED`를 자동으로 뜻하지 않는다. 검증 근거가 없으면 `VERIFIED`를 쓰지 않는다. 상태 변경은 [문서 등록부](document-register.yaml), [계약 레지스트리](../contracts/registry.yaml), 관련 PR에서 함께 추적한다. 승인자·시각·PR이 알려지지 않았으면 `null`로 둔다.

## 계약과 revision

계약마다 고유 ID, 버전, artifact 경로와 SHA-256, 문서 승인 상태, 제공자·소비자, 관련 TD와 PR, 실제 구현 commit, 검증 commit·범위, 호환성 판단을 기록한다. 현재 Spring 기대 계약과 Specs proposal을 별도로 기술한다. 계약 revision은 승인된 Specs commit SHA와 artifact SHA-256으로 고정하고 구현 PR이 이를 참조한다. 계약 파일의 버전 문자열만 같아도 내용 해시가 다르면 다른 revision이다. 현재 구현 SHA와 목표 계약 구현 SHA를 혼동하지 않는다.

필수 필드 추가·삭제, 경로·상태·오류 코드·enum 의미 변경처럼 기존 소비자가 해석할 수 없는 변경은 Breaking Change 후보로 본다. 제공자와 소비자의 실제 DTO·fixture를 비교해 하위 호환 여부를 판단하고, 승인 전에는 계약을 확정하지 않는다. Breaking Change에는 구버전 공존 또는 순차 전환 계획, 배포 순서, 실패 시 복귀 방식, 연결된 저장소별 PR이 필요하다. 오래된 revision은 삭제하지 않고 `DEPRECATED` 상태와 대체 revision을 남긴다. fixture가 존재하지 않으면 경로를 지어내지 않는다.

## PR과 동기화

하나의 논리적 기능이 여러 저장소에 걸치면 각각의 저장소에서 연결된 PR을 관리한다. 한 PR이 모든 저장소를 동시에 변경한다고 가정하지 않는다. PR에는 현행 코드와 목표 설계의 차이, 승인 상태, 호환성 검증, 소비자·제공자의 적용 순서와 테스트 결과를 기록한다. 다른 저장소의 변경은 해당 작업의 명시적 승인 범위 안에서만 수행한다. 문서 변경은 관련 TD 이슈에 연결하며 실제 GitHub Issue나 PR이 없으면 번호나 링크를 지어내지 않는다.

원본 문서를 바꾼 경우 통합본의 동일한 절만 갱신하고 `00`~`15` 전부의 순서와 본문 일치 여부를 확인한다. 통합본 단독 변경은 허용하지 않는다. API 키·인증 토큰·HMAC 키·개인정보 원문은 문서와 fixture에 포함하지 않는다. 합성 예시만 사용하며 분석 오류를 정상적인 빈 결과로 표현하지 않는다.

## Git 커밋 메시지와 이력

Ticket Defender 모든 저장소에 제안하는 공통 형식은 `<type>(<scope>): <한글 작업 요약>`이다. scope는 선택 사항이고 생략하면 `<type>: <한글 작업 요약>`으로 쓴다. type은 영어 소문자, 콜론 뒤에는 공백 한 칸을 둔다. 요약은 실제 변경을 짧고 명확한 한글로 적고 서로 다른 목적은 가능한 한 별도 커밋으로 나눈다. 테스트하지 않은 내용을 검증 완료로 주장하지 않는다.

| type | 용도 |
|---|---|
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `test` | 테스트 관련 변경 |
| `refactor` | 기능 변화 없는 구조 개선 |
| `chore` | 일반 유지보수·개발 환경 |
| `ci` | CI/CD 설정 |
| `perf` | 성능 최적화 |
| `build` | 빌드 시스템·의존성 변경 |
| `revert` | 이전 변경 되돌리기 |

API·DB 계약 변경 시 필요하면 커밋 본문에 관련 TD와 영향을 받는 제공자·소비자 범위를 적는다. Breaking Change는 Conventional Commits의 `!`(예: `feat(api)!: ...`) 또는 `BREAKING CHANGE:` footer로 표시하고 호환성·전환 영향을 설명한다. 여러 저장소의 관련 커밋은 각각의 SHA와 PR을 연결해 추적한다. 이미 공유되거나 원격에 반영된 이력은 무단 재작성하지 않으며, 재작성 전 공유·원격 상태와 명시적 승인을 확인한다. 사용자 승인 없이 commit/push하지 않는다.
